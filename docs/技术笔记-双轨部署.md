# 技术笔记：双轨部署

## 概述

一种把静态发布和源码推送拆成两条链路的 **双轨部署技术**。

其核心特征是：

- 用 A 线面向静态页面仓库；
- 用 B 线面向 Vercel 源码仓库；
- 用独立 SSH Key 隔离不同推送权限；
- 用 Git 命令自动提交并推送本地代码。

## 分类

所属分类：组件架构

## 核心技术内容

### 技术原理

部署设置页把 GitHub Pages 静态发布和 Vercel 源码托管拆成两组配置。A 线用于 `gh-pages` 静态产物，B 线用于把完整源码推送到 GitHub，再触发 Vercel 自动构建。B 线使用单独的 `id_ed25519_source`，并在推送时通过 `GIT_SSH_COMMAND` 强制 Git 使用这把钥匙。

### 核心实现

```py
config = {
    "blogPath": "",
    "staticRepoUrl": "",
    "staticBranch": "gh-pages",
    "sourceRepoUrl": "",
    "sourceBranch": "main",
}
```

```py
priv_key_path = os.path.join(ssh_dir, "id_ed25519_source").replace("\\", "/")
custom_env = os.environ.copy()
custom_env["GIT_SSH_COMMAND"] = (
    f'ssh -i "{priv_key_path}" '
    "-o IdentitiesOnly=yes -o StrictHostKeyChecking=no"
)

subprocess.run(
    f'git push "{source_repo}" HEAD:{source_branch}',
    shell=True,
    env=custom_env,
)
```

### 参数说明

| 参数 | 作用 | 推荐值 | 说明 |
|------|------|--------|------|
| `staticRepoUrl` | A 线仓库地址 | SSH 地址 | 存放静态产物 |
| `staticBranch` | A 线目标分支 | `gh-pages` | GitHub Pages 常用分支 |
| `sourceRepoUrl` | B 线仓库地址 | `git@github-source:...` | 存放源码并触发 Vercel |
| `sourceBranch` | B 线目标分支 | `main` | Vercel 默认监听分支 |
| `commitMessage` | 自动提交信息 | 可留空 | 留空使用默认信息 |

### 方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| A 线静态发布 | 托管简单、访问成本低 | 无法运行 API Route | 纯静态博客 |
| B 线源码推送 | 支持 Next API、Vercel 构建 | 依赖仓库和构建平台 | 评论、音乐、AI 需要服务端代理 |
| 手动 Git 命令 | 可控性高 | 对用户不友好 | 开发者维护 |

### 设计要点

- GitHub 登录评论依赖 `/api/github`，因此需要 B 线或其他支持服务端函数的部署；
- A/B 两线使用不同 SSH Key，避免一个 Deploy Key 承担过多权限；
- 保存部署配置到 `data/deploy_config.json`，控制台重启后仍能读取；
- 推送前先 `git add .` 和 `git commit`，没有变更时继续尝试 push。

## 适用场景

- 博客既要静态托管又要服务端代理时；
- 希望一键推送 GitHub 并触发 Vercel 构建时；
- 多仓库、多分支部署路径需要分离时；
- 用户不希望手写 Git 命令时。

## 注意事项

- Deploy Key 若勾选写权限，应只绑定到对应仓库；
- 如果使用 A 线静态发布，需要确保构建产物目录和 Next 配置匹配；
- B 线推送失败时优先检查 SSH 地址、Deploy Key 权限和目标分支。
