# 技术笔记：持久化操作队列

## 概述

一种通过结构化操作、磁盘持久化和分阶段同步控制内容发布的 **操作队列技术**。

其核心特征是：

- 使用判别联合约束操作类型与载荷；
- 使用本地 JSON 保存刷新后的待办状态；
- 使用同步计划冻结源文件摘要与目标状态；
- 使用任务编号查询提交和推送进度。

## 分类

所属分类：组件架构

## 核心技术内容

### 技术原理

界面操作先进入 `operations.json`，不会因刷新丢失。发布阶段不直接执行覆盖，而是先生成差异计划；应用计划时重新验证源摘要和 Git 状态；推送阶段再保存文件快照，防止排队后内容被替换。

### 核心实现

```ts
type Operation = {
  id: string;
  type: "content_upsert" | "content_delete" | "settings_update";
  label: string;
  timestamp: string;
  payload: unknown;
};
```

```text
POST /api/sync/plan
  -> POST /api/sync/apply
  -> POST /api/deploy/push

```

class ApplyRequest(BaseModel):

### 参数说明

| 参数 | 作用 | 推荐值 | 说明 |
|------|------|--------|------|
| `type` | 操作分类 | 固定联合类型 | 后端拒绝未知操作 |
| `payload` | 结构化载荷 | JSON 数据 | 不使用源码字符串拼接 |
| `planId` | 同步计划标识 | 32 位十六进制 | 阻止路径穿越并绑定计划 |
| `sourceDigest` | 源文件摘要 | SHA-256 | 预览后变化会使计划失效 |
| `jobId` | 发布任务标识 | 32 位十六进制 | 用于轮询进度与错误 |

### 状态说明

| 状态 | 含义 | 可执行动作 |
|------|------|------------|
| `queued` | 等待 Git 任务 | 继续查询 |
| `running` | 正在提交或推送 | 禁止重复提交 |
| `succeeded` | 已推送远程 | 检查 Vercel Preview |
| `failed` | 任务失败 | 根据错误处理后重试 |

### 设计要点

- 目标仓库必须在计划和应用阶段保持干净；
- 同步只删除上一份清单记录的过期文件；
- 文件替换前创建备份，失败时恢复旧文件和清单；
- Git 只暂存允许路径，不使用 reset 或 force push。

## 适用场景

- 管理端需要“暂存、预览、执行”工作流；
- 多类内容共享一个发布仓库；
- 长任务需要进度查询和重复提交控制；
- 文件同步必须保护未知目录与用户改动。
