# 技术笔记：评论系统

## 概述

一种通过 GitHub Issues 存储留言并用同源代理完成 OAuth 的 **Gitalk评论技术**。

其核心特征是：

- 用 Gitalk 渲染评论输入和列表；
- 用路径生成稳定 Issue 标识；
- 用 `/api/github` 代理 OAuth 换取 Token；
- 用控制台维护 OAuth 和仓库配置。

## 分类

所属分类：组件架构

## 核心技术内容

### 技术原理

评论组件读取 `siteConfig.gitalkConfig`，将 GitHub OAuth App、评论仓库、仓库所有者和管理员列表传给 Gitalk。登录回调后，Gitalk 会把授权码提交到 `proxy`，项目中的 `/api/github` 再转发到 GitHub OAuth 接口，避免浏览器直接请求 GitHub token 接口导致跨域失败。

### 核心实现

```ts
const gitalk = new Gitalk({
  clientID: siteConfig.gitalkConfig.clientID,
  clientSecret: siteConfig.gitalkConfig.clientSecret,
  repo: siteConfig.gitalkConfig.repo,
  owner: siteConfig.gitalkConfig.owner,
  admin: siteConfig.gitalkConfig.admin,
  proxy: "/api/github",
  id: (pathname.replace(/\/$/, "") || "/").substring(0, 49),
});
```

```ts
export async function POST(req: Request) {
  const body = await req.text();
  const githubRes = await fetch("https://github.com/login/oauth/access_token", {
    method: "POST",
    headers: {
      "Content-Type": req.headers.get("content-type") || "application/json",
      "Accept": "application/json",
    },
    body,
  });
  return NextResponse.json(await githubRes.json());
}
```

### 参数说明

| 参数 | 作用 | 推荐值 | 说明 |
|------|------|--------|------|
| `clientID` | OAuth App 标识 | GitHub 生成 | 不能为空 |
| `clientSecret` | OAuth App Secret | GitHub 生成 | 不建议暴露在公开仓库 |
| `repo` | Issues 仓库名 | 公开仓库 | 用于存储评论 |
| `owner` | 仓库所有者 | GitHub 用户名 | 必须与仓库匹配 |
| `admin` | 评论管理员 | 用户名数组 | 可初始化 Issue |
| `proxy` | OAuth 代理 | `/api/github` | 需要 Next API Route 可用 |

### 网络错误排查

| 检查项 | 现象 | 处理 |
|------|------|------|
| `gitalkConfig` 为空 | 评论框出现但登录或加载失败 | 在控制台评论设置填写并更新本地、同步 Blog |
| 纯静态部署 | `/api/github` 返回 404 或 HTML | 使用 Vercel/Node 部署，或换可用代理 |
| Callback URL 不匹配 | GitHub 授权后无法正常回跳 | OAuth App 填写实际博客域名 |
| Issues 仓库非公开 | Gitalk 无法读写评论 | 使用公开仓库存储评论 |
| GitHub 网络受限 | 直接请求 GitHub API 失败 | 检查网络、代理或稍后重试 |

当前项目里 `YunYueBlog/siteConfig.ts` 的 `clientID`、`clientSecret`、`repo`、`owner` 为空，所以截图中的 `Error: Network Error` 最可能先由评论配置未落盘或未同步引起；如果配置已填写，则下一步检查线上 `/api/github` 是否可访问。

### 设计要点

- `id` 截断到 49 字符，符合 Gitalk 对 Issue Label 长度的限制；
- 登录成功后清理 URL 中的 `code`，避免退出后二次登录使用旧凭证；
- 评论区样式通过全局 CSS 覆盖 Gitalk 默认样式；
- 需要服务端代理，因此发布端不能只做纯静态导出。

## 适用场景

- 个人博客希望用 GitHub Issues 承载留言时；
- 评论量不大且愿意依赖 GitHub 账号登录时；
- 站点已部署到支持 API Route 的平台时；
- 希望评论数据与代码仓库生态保持一致时。

## 注意事项

- 更安全的方案是把 OAuth Secret 留在服务端，由服务端补齐 token exchange 请求；
- 评论仓库建议单独创建，避免把博客源码仓库开放为 Issues 评论区；
- OAuth Callback URL 必须使用最终访问域名，本地调试则另建或修改为本地地址。
