# LX Music 音源架构与本博客适配评估

核对日期：2026-11-03。研究仓库为 [lyswhut/lx-music-desktop](https://github.com/lyswhut/lx-music-desktop)，固定研究提交 `ad95d5091c9ed689fa72b5e5c849df65f5a679ce`，该提交 package.json 版本为 2.12.6。本次阅读上游代码，并用用户提供的墨澜 2.3.4 音源在隔离 QuickJS 宿主中完成当前 12 首歌单实测；未安装或运行完整 LX 桌面程序，未改变线上取源配置。

## 当前结论

**保留 LX 音源作为可选方案，不因 HTTPS 检测结果将其排除。** 这份脚本在未提供任何音乐账号、Cookie 或用户环境变量的条件下，为当前 12 首歌全部取得原始 HTTP 地址。12 首的小范围音频请求均为 HTTP 206，MP3 帧头均为 320 kbps，浏览器均加载了完整曲目时长且播放时间推进超过 0.3 秒；12 首文件末尾的 4 KB Range 也全部返回正确的 206 与字节数。

这证明当前歌单取源及开始播放成功，不等于整首听完、所有会员曲目均可用、其他平台均已验证，或第三方服务长期稳定。LX 兼容协议本身没有统一 VIP 登录门槛；实际能否解析歌曲、音质和完整文件，取决于选定音源的上游。不能把原账号接口的会员限制直接套到这个音源。

**Vercel 的关键是音频正文的传输路径。** 原账号与 LX 两种方案都可以让音频绕过 Vercel：有效 HTTPS 由浏览器直连，其余走独立 Cloudflare Worker。LX 的额外价值在本轮是无账号取源、两首从 128 提升为 320，以及减少部分边缘中转量；不是只有引入 LX 才能避免 Vercel 音频流量。

## 2026-11-03 墨澜 2.3.4 实测

### 测试方法与修正

- 使用用户指定的本地文件；脚本 SHA-256：`328e06c473dfc0ba6de338a7b04f00e3b67a69f59205ca6903d553a80b57c706`。未将脚本、完整签名地址、第三方接口密钥或用户凭据放入公开仓库。
- 独立 QuickJS WASM 上限 48 MB；没有 require/process/文件系统或用户账号。宿主仅提供 LX 事件、受控 HTTP、Buffer、crypto、zlib 和计时器；有网络目标、请求次数、超时与响应大小限制。
- 已对照 LX 2.12.6 的实际 preload 请求格式与酷狗目录字段。最终输入使用官方目录查询取得的 AudioID、album_audio_id，以及不同音质对应的真实 Hash；没有把标准 Hash 当成 HQ Hash。
- 初版测试器误拦全部 IP 字面量，已修正为允许公网 IP、继续拒绝私网。修正后脚本自身的一个公网 IP 备源超时，再回退成功；最终轮每首解析约 5.6 秒，不能当作所有网络环境的固定耗时。
- 取源结果全部保留原始 HTTP 协议。HTTPS 是**额外的网页适配检查**：只改变同一地址的协议，不更换域名，不忽略证书错误。
- 24 项浏览器检查在本地 HTTP 诊断页进行：12 个原始地址及其 12 个 HTTPS 版本。每项静音播放，推进超过 0.3 秒后停止；未完整下载并收听全曲。真实 HTTPS 站点的自动升级路径未完成独立浏览器验收，下述混合内容解释依据浏览器规范。

### 为什么 LX 能播，HTTPS 博客会出现域名差异

这不是“12 首只有 5 首取源成功”：**12 首取源与原始地址播放全部成功。** 5/7 区分的是可否使用同一地址建立有效 HTTPS 连接。

- `fsandroid.tx.kugou.com` 本轮证书覆盖 `*.tx.kugou.com`，5 首 HTTPS Range 与浏览器实播均成功。
- `fs.youthandroid2.kugou.com` 本轮 HTTPS 返回的证书不覆盖该域名，7 首得到 `ERR_TLS_CERT_ALTNAME_INVALID`，浏览器亦失败；HTTP Range 和实播全部成功。
- LX 的[主播放窗口](https://github.com/lyswhut/lx-music-desktop/blob/ad95d5091c9ed689fa72b5e5c849df65f5a679ce/src/main/modules/winMain/main.ts)使用本地文件页面，并设置 `webSecurity: false`。这与音源执行窗口是两个不同窗口，不能混淆。
- 普通 HTTPS 网页中的 HTTP `<audio src>` 属于会被升级到 HTTPS 的混合内容，不能要求访客修改浏览器安全设置。见 [MDN 混合内容说明](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Mixed_content)。因此在当前域名与证书条件下，7 首应使用独立边缘中转，或等待音源返回实际签发的 HTTPS 备源。

CDN 分配、签名地址和证书均可能变化；5/7 是这次歌单快照，不是按歌曲永久固定的规则。不凭猜测替换 CDN 域名。

### 按实际文件大小比较传输

假设当前 12 首每首完整播放一次，不命中已下载的浏览器缓存，不拖动、不重试；1 MB = 1,000,000 字节。使用 Content-Range 的总文件长度估算，不是已经播放或实际计费的全部流量。

| 方案 | Vercel 音频正文 | 独立 Cloudflare 音频正文 | 访客收到音频 |
| --- | ---: | ---: | ---: |
| 当前账号，HTTP 仍由 Vercel 中转 | 104.94 MB | 0 | 104.94 MB |
| 墨澜，5 首 HTTPS 直连、7 首 Vercel 中转 | 71.49 MB | 0 | 120.34 MB |
| 当前账号，HTTP 改走独立 Cloudflare | 0 | 104.94 MB | 104.94 MB |
| 墨澜，5 首 HTTPS 直连、7 首独立 Cloudflare | 0 | 71.49 MB | 120.34 MB |

- 墨澜的中转字节比当前账号快照少约 **31.87%**；当前账号有两首只能取得 128 kbps，墨澜两首均为 320，故两种方案并非完全相同音质。
- 墨澜总音频文件量增加约 **14.68%**。音源脚本改变的是解析途径和可用音质，并不压缩音频。
- 最终轮音源上游成功解析响应共约 **10.33 KB / 12 首**，不含请求头、TLS、超时连接和博客返回给访客的 JSON；不能把这个数当成整轮 Vercel 账单。正式接入需要同曲并发合并及短期 URL 缓存。
- 若仍由 Vercel 中转，按用户设定的 10 GB / 30 天预算、仅计音频，约 95 轮当前账号歌单或 140 轮墨澜歌单会耗尽预算；页面、字体、图片、响应头、拖动、重试和缓存策略会改变结果。
- 若走独立 Cloudflare，音频正文不经过 Vercel，但解析接口和页面资源仍可能计 Vercel 用量。此表是可审查的目标数据路径，**没有完成线上配置或部署**。

Cloudflare Workers 仍有请求数、CPU 与数据库限额。当前[官方定价](https://developers.cloudflare.com/workers/platform/pricing/)列出 Free 每日 100,000 次请求、每次 10 ms CPU；不能将“离开 Vercel”描述成没有任何额度。第三方脚本的 WASM 执行开销还需单独测量，不能直接假定免费 Worker 可承担完整兼容宿主。

### 本次决定

优先完成音频与 Vercel 解耦。保留这份脚本作为后续可选解析适配器，其无账号取源及两首音质提升已经有本地证据；不把完整 Electron 桌面工程搬进博客，也不因本轮 7 首缺少有效 HTTPS 而否定该音源。是否正式接入兼容宿主，应以宿主 CPU、稳定性、边缘取源连通性和实际运维成本继续验收。

### 新一轮取源核对

重新执行完整 12 首取源，并对本次实际返回的同域名 HTTPS 地址进行 1 KB Range 请求与严格 TLS 校验，结果为 **9/12 可建立有效 HTTPS 并返回 206**。另外三首：《玄翎谣》、《星が瞬くこんな夜に》、《远航星的告别》，重新取源后仍未取得可通过校验的 HTTPS 地址。

本轮《天上飞琼》《蒼崎青子》《久遠寺有珠》等已分配到有效 HTTPS 节点，《远航星的告别》则从此前有效节点变成不匹配节点。先前 5/7 是第一轮快照；新一轮 9/3 也不是永久划分。新增检查是网络/TLS/Range 验证，不冒充已经完成全部新地址的浏览器实播。

额外检查了两首的音源上游解析 JSON：每首只返回一个音频 URL，未发现被当前宿主遗漏的音频备源数组；notice 中的 HTTPS 网页不是音频备源。不能通过把 notice 或其他普通网页当播放地址来补齐 HTTPS。

### 可实现的边界

1. **原音乐 CDN 全部原生 HTTPS 直连：无法仅通过修改 LX 保证。** 可以增加备源收集、严格 HTTPS 健康检查、有限重取、同曲并发合并、短期缓存和失效更新。证书、节点分配、签名与源站协议由上游控制；不能凭空生成上游证书，也不能通过无限重试作保证。
2. **浏览器统一使用 HTTPS 播放：可以。** 有效的原站 HTTPS 直接使用；其余交给独立 Cloudflare Worker 的自有 HTTPS 地址。后者属于 HTTPS 中转，并非浏览器直连原音乐 CDN。
3. 如果上游只支持 HTTP，浏览器到 Worker 是 HTTPS，Worker 到上游仍是 HTTP；这不构成两段链路都使用 HTTPS。服务不关闭 TLS 校验、不要求访客修改浏览器安全设置。
4. **两种路径都能让音频正文离开 Vercel。** 所有曲目都强制通过 Cloudflare，与有效 HTTPS 直连加 Cloudflare 兜底，对 Vercel 的音频正文目标都为 0。后者可减少 Cloudflare 请求、带宽和一次转发路径。

### 音质与传输方式

Worker 按原始字节流转发，保留 HTTP Range、Content-Range、Content-Length 和媒体类型；不进行解码重编码、重采样或码率转换。上游提供 320 kbps，输出仍为同一份 320 kbps 文件。传输不会提升或降低源文件音质；网络速度会影响缓冲与连接稳定性。

将来若开启 FLAC，同样可采用原样转发，但需要单独适配浏览器能力与文件大小策略。现有候选代码仍只允许核实的 128/320 kbps MP3，并有 32 MB 单响应保护，不能声称已完成全格式支持。

### Cloudflare 当前额度与费用

以 2026-11-03 查询的 [Workers 定价](https://developers.cloudflare.com/workers/platform/pricing/)和[运行限制](https://developers.cloudflare.com/workers/platform/limits/)为依据：

| 项目 | Workers Free | Workers Paid Standard |
| --- | --- | --- |
| 基础费用 | 0 | 最低 5 美元 / 月 |
| 入站请求 | 每账号每天 100,000 次 | 每月包含 10,000,000 次，超出 0.30 美元 / 百万次 |
| CPU | 每次 10 ms | 每月包含 30,000,000 CPU-ms，超出 0.02 美元 / 百万 CPU-ms |
| CPU 单次上限 | 10 ms | 默认 30 秒，可设至 5 分钟 |
| HTTP 响应体大小 | 无平台强制响应体上限，需流式输出 | 同左 |
| HTTP 连接时长 | 客户端保持连接时无固定硬上限，仍可能断连 | 同左 |

官方定价没有为 Workers 列出类似“10 GB / 30 天”的音频传输包；Paid Standard 明确不额外收取出口流量或带宽费。Free 主要以请求数和 CPU 限额控制，并非无限计算、无限请求或任意用途保证。每日请求在 UTC 00:00，即北京时间 08:00 重置；同账号其他 Workers 共享额度。拖动、重连、重试及 Range 请求可能增加入站请求数，不能把 100,000 次直接换算成 100,000 首播放。

等待网络的时间不计为 CPU，音频播放数分钟不等于执行代码数分钟。但 HMAC、数据库操作、流处理和第三方脚本引擎会消耗 CPU；完整 LX 兼容宿主尤其需要独立测量，不能仅因流量不按 GB 计费就保证 Free 足够。数据库与其他绑定另有额度。

[普通 CDN 的服务条款](https://www.cloudflare.com/service-specific-terms-application-services/#content-delivery-network-terms)对大量音频与大文件分发另有限制，不能把免费橙云代理当无限媒体 CDN；[开发平台条款](https://www.cloudflare.com/service-specific-terms-developer-platform/)也保留对过重负载的限制。Workers、R2、普通 CDN 与 Containers 是不同产品；Containers 还可能按出口 GB 计费，不能套用 Workers 定价。

目前代码中的默认 `MUSIC_DELIVERY_BUDGET_BYTES=1000000000`、最高可配 10 GB 和 32 MB 单响应都是本项目设置的保护阈值，**不是 Cloudflare 套餐限制**。正式落地应把平台请求/CPU余量、累计传输监控和本站防滥用策略分开，避免迁出 Vercel 后仍机械沿用 Vercel 的字节阈值。

### 本项目推荐

优先采用「有效原站 HTTPS 直连 + 独立 Cloudflare 无转码兜底 + Vercel 不传音频正文」。既有账号适配器与后续 LX 兼容适配器共享这层传输策略。复杂解析宿主与轻量音频转发分开部署，避免解析 CPU、第三方代码或音源故障影响管理后台。

本次增加了本地取源/TLS 检查原型与方案依据，未部署独立 Worker、未改变线上音乐路径、未订阅付费服务；尚不能将方案写成已经上线。当前候选代码的音频路由仍附属管理 Worker，独立音频服务与边缘出口验收属于后续实施项。

## 已追踪的实际调用链

1. 设置界面导入本地 JS，或通过 URL 下载脚本文本。
2. 主进程解析脚本头的名称、版本、作者、主页等元数据，压缩保存脚本快照。
3. 选择一个当前使用的自定义源，启动隐藏的 Electron BrowserWindow。
4. preload 通过 contextBridge 暴露 `globalThis.lx`，提供事件、HTTP 请求、加密、Buffer 和压缩接口。
5. 脚本注册 request 回调，并发送 inited，声明支持的平台、动作和音质。
6. 播放器请求 musicUrl，经 IPC 和 requestKey 路由到脚本；结果通过校验后返回播放器。
7. 在线播放层先查 URL 缓存，失败后可搜索并尝试其他平台上的同曲候选。

## 容易混淆的边界

- **音源脚本与音乐平台不是一回事。** `wy`、`kg` 等是歌曲平台，脚本是为这些平台解析 URL 的适配器。当前选择一个脚本，该脚本可同时支持多个平台；源码没有直接提供“所有导入脚本依次回退”的通用链。
- **音源脚本不等于完整的搜索、歌单、评论服务。** 网易云和酷狗 SDK 仍有独立搜索、歌单、歌词、封面实现。常规平台脚本动作主要是 musicUrl；`local` 分支还支持 lyric 和 pic。
- **在线导入不是自动订阅更新。** 已读实现会下载并存储当前脚本内容；更新提示有单独机制，不能将其解释为自动下载、自动启用新版本。
- **取消等待不等于底层请求已停止。** 宿主移除 requestKey，迟到结果会被丢弃；needle 的中止函数由请求桥返回，脚本是否使用它是另一个环节。本博客需要同时传播 AbortSignal 并忽略过期结果。
- **local 源不表示把本机路径发布给访客。** 浏览器访客无法读取站长电脑文件，自有音频必须先上传到可公开访问的存储。
- 仓库默认自定义源列表为空，并不自带第三方服务稳定性或播放授权保证。没有具体源脚本，不能声明“兼容全部洛雪音源”。

## 对现有工程的建议

### 第一阶段：完成当前后台与内置账号

- 管理歌单、曲目排序、歌词覆盖与偏移、网易云/酷狗二维码登录、账号可用状态。
- 歌曲目录保留现有 key；临时播放 URL 不写回歌单或公开 Git。
- 每次解析统一返回歌曲标识、质量、URL、有效期、来源适配器和是否需要受控中转。
- 合并同曲并发请求，按凭据版本区分缓存，失效后刷新；登录更换时使原账号缓存失效。
- 维持当前“优先 320、没有 320 才使用 128”的选择，不照搬桌面端无损优先配置。

### 第二阶段：第三方 HTTP 适配器

适合目标是少量可靠服务、低维护成本的情况。配置导入可用声明式 JSON：服务名、固定 HTTPS 接口、支持平台和音质、超时、允许返回的媒体域名等；密钥另存服务端，不混入公开配置。

这不是 LX 脚本格式，也不应在界面上标注为兼容 LX。它不需要在后台执行上传的 JS，维护成本较低。

### 第三阶段：完整 LX 兼容服务（可选，实测后保留）

若必须直接导入社区 JS，应建立独立的兼容宿主，提供 lx.request、事件、crypto、buffer、zlib 和能力协商。仅有 `eval`、Function 或 Node vm 上下文不足以当成不可信脚本的隔离边界。

需要按脚本版本固定内容与哈希，导入后先测试、再启用，失败可回滚。执行环境隔离于管理会话、数据库和音乐账号凭据；网络出口、并发、CPU、内存、响应大小和媒体 URL 均有限额。上传脚本不应默认获得博主平台 Cookie。

免费 Vercel/Cloudflare 常规函数无法原样承载 Electron 隐藏窗口。独立服务或受限 JS 引擎的实现与部署成本需要另评估；选择的实际脚本必须做逐项兼容验证。

## 流量与体验

第三方脚本只改变 URL 的获得方式，不自动消除音频传输。320 kbps 每小时约 144 MB，128 kbps 约 57.6 MB。按 10 GB 十进制粗算，累计约 69 或 174 小时即到上限，尚未计响应开销和其他资源。

- 优先返回浏览器可直连的 HTTPS 音频；需要 Cookie、特定 Referer、HTTP 转 HTTPS 或格式转换的源必须单独评估中转。
- 普通博客页面不预载整份歌单音频。LX 临近下一曲时使用隐藏 Audio 的策略适合桌面应用，本项目应先限于地址预取，保持点击播放才加载音频。
- 同曲回退必须校验歌手、时长与版本，避免换成翻唱、现场或不同编曲后歌词失配；不应只凭同名自动替换。
- 保留原始平台标识、失败原因与手动切换；临时签名地址不进入日志、配置导出或截图。

## 研究与实施边界

本次已在独立隔离宿主中测试用户提供的本地墨澜脚本，没有安装或运行完整 LX 桌面程序，没有导入在线脚本，也没有修改正式博客的取源顺序。当前账号后台继续保留。临时测试宿主与包含签名 URL 的原始数据仅留在被忽略的本机诊断目录中，不作为已完成的生产兼容层。

上游代码采用 Apache-2.0。若实际复用代码，需要保留相关许可证与归属；本次评估及当前后台实现使用自己的代码与本站布局。


## 2026-11-03 实施结果与音质选择

以上阶段建议已进入实现：采用受限 QuickJS 宿主，并在控制台提供本地 JS / HTTPS 下载、加密暂存、按歌单测试、启用和停用。当前仅承诺已验证脚本的能力范围。正式博客返回原站有效 HTTPS 或独立音频 Worker 票据，不再以 Vercel 函数传输 HTTP 音频正文。

默认保留 320 kbps，允许访客选择“最高兼容 · 优先 FLAC”。可用无损失败时有限回退至 320/128，浏览器 FLAC 解码失败自动回退 320。切换保留歌曲和进度，取消旧批次，歌单缓存区分音质；不预下载整份音频。DSD、母带、Atmos 等不纳入网页播放器支持范围。

| 类型 | 约每小时数据量 | 取舍 |
| --- | --- | --- |
| 320 kbps MP3 | 144 MB | 默认，兼顾移动网络和浏览器兼容性 |
| CD 双声道 PCM，16bit/44.1kHz | 635 MB | 为未压缩参照，不是所有 FLAC 的实际体积 |
| 24bit/96kHz 双声道 PCM | 2.07 GB | 更高缓冲和访客流量成本，不设为默认 |
| FLAC | 随音源和压缩率变化 | 本轮同曲样本约 19.9 MB，320 MP3 约 6.4 MB，约 3.1 倍 |

不经过 Vercel 只消除该平台的**音频正文传输**，页面、字体、图片、元数据解析和 Node CPU 仍消耗相应额度。提高音质仍会增加访客流量、加载时间、解码负担，以及 Cloudflare 的连接/流处理工作；不能由此推导“最高音质没有成本”。

### Cloudflare 费用与容量

2026-11-03 核对官方文档：Workers Free 每账号 100,000 请求/日、每次 10ms CPU。Paid Standard 最低 5 美元/月，包含请求与 CPU 用量，官方说明不另收出口 GB/带宽费。D1 免费额度另外限制每日读写行数；当前预算计数每次播放会写入数据库，可能先于 Worker 请求上限耗尽。普通 CDN 的大文件条款和开发平台使用条款仍适用，不能称为无限免费音乐 CDN。

本实现的字节预算默认 0，表示只记录**预留量**，可配置正整数硬限额；并非服务商真实账单或精确已传输量。取消播放不会返还预留。使用约 31 个 UTC 日桶保守统计。另设 40,000 次/UTC 日的本站传输请求保护，为解析、D1 及管理请求留余量；它不是 Cloudflare 账户统计，不能保证覆盖同账号其他项目用量。

### 本地验证与剩余边界

正式 Node 模块已解析出真实 320 kbps 与 FLAC。当前 12 首歌单均取得 320 kbps 地址；CDN 分配会变化，不能把 5/7 或 9/3 固定为永久可用比例。对一个真实 FLAC 样本，原站与本地 Worker 模拟的 `bytes=1024-5119` 均返回 206、4096 字节、哈希完全一致。仅说明抽样传输字节未变化，不代表逐首整曲听完。

独立音频 Worker 构建已通过，尚未部署；本地人工预览复用管理 Worker 的同一传输函数。生产出口地域是否能访问第三方 CDN、免费 CPU 是否足够、真实手机弱网，以及新的 Vercel WASM 部署产物仍需部署后检查。扫码和图床流程完成隔离模拟验收，未替站长确认真实扫码或真实上传。


### 当前实现补充：五渠道目录与自定义源唯一入口

音乐工作台按已启用音源能力提供网易云、酷狗、QQ、酷我、咪咕的模糊目录检索；界面不再提供平台账号及手动排轴。搜索是元数据请求，每页 15 条，显式提交，支持缓存回切与旧请求隔离；搜索不到时可换关键词或渠道，无需精确 ID。自动歌词与发布后的播放链路保留。

QQ 脚本计算较重，单个隔离解析最多 8 秒 CPU、约 21 秒墙钟，并发最多 2；不同质量回退仍受同一截止时间约束。真实抽样中酷我取得 HTTPS 320 kbps，咪咕取得 HTTPS 实际 128 kbps；QQ 样本的 Range 数据不识别为 MP3/FLAC，当前拒绝播放，未绕过格式校验，也未引入解密/转码。所有五渠道目录查询均取得结果，不能把目录可搜等同于歌曲可播或最高音质可用。

音质只由控制台配置，博客无选择器；实际音质与站长偏好可能因音源能力、浏览器解码或有限回退而不同。通过原站或 Cloudflare 传音频仍消耗访客流量与对应服务资源，Vercel 保留页面、元数据及有限探测开销。本轮没有生产部署或付费扩容。
