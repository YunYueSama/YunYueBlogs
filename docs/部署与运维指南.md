# 部署与运维指南

本文对应在线创作间与 Astro 公开站。旧版 `my-blog-manager` 是保留的本地工具，其 Next.js / FastAPI 启动方式不适用于新控制台。

## 准备自己的环境

Fork 两个仓库：本仓库管理云端创作间，`YunYueBlog` 仓库管理公开站。Node 版本按各 `package.json` engines，安装 Git，登录自己的 Cloudflare 与 Vercel。

修改 `apps/console/cloudflare.config.ts`、`music-worker/cloudflare.config.ts` 的 Worker、D1 名称、管理域名、音频域名、目标 GitHub 仓库和 `SITE_URL`；公开站同步修改域名与页脚管理入口。不要复用作者的生产绑定。

使用 `cf cli search "任务描述"` 找命令，执行前阅读当前版本 `--help`，新建资源和部署先 `--dry-run`。此项目使用 cf CLI 和 `cloudflare.config.ts`，不另建 Wrangler 配置。

## 1. 部署 Node 服务

将 `services/password-verifier` 作为独立 Vercel 项目根目录，运行 `npm ci`、`npm test`、`npm run build`。按服务端秘密配置 `PASSWORD_SERVICE_KEY`，保留 `vercel.json` 的 QuickJS WASM 与生成包 includeFiles。

部署后记录 `/api/password` 完整 URL，确认未授权请求返回 401，并以私有内部请求验证随机密码 hash / verify 与音源声明解析。不要输出认证头或原始媒体 URL。

## 2. 创建 D1、初始化账号与公开内容

在控制台目录安装依赖，创建自己命名的 D1。核对名称和数据库 ID，再应用本目录两份 migration：

```powershell
npx cf d1 migrations apply <database-id> --dir migrations --dry-run
npx cf d1 migrations apply <database-id> --dir migrations
```

通过私有进程环境提供 `CONSOLE_ADMIN_USERNAME`、`CONSOLE_INITIAL_PASSWORD`，运行 `scripts/prepare-admin.mjs <ignored-output.json>`。它生成参数化初始化批次及单独激活文件，不直接改库。密码没有默认共享值，不写在命令历史和公开文档里。

用 `cf d1 query --help` 确认批次参数，再将私有文件通过 `--batch @<path>` 写入目标空库。24 小时内用 `https://<admin-domain>/?activate=<ticket>` 打开登录页，首次登录必须改密。激活票据只私下交给站长，不记录在 Issue、截图和公共日志。

`node scripts/import-public.mjs <ignored-output.json>` 从博客白名单生成公开内容导入批次，跳过 `draft: true`；核对后写入自己的库。重复导入不覆盖云端现有编辑。

迁移已有控制台时，备份 `admin_users`、`documents`、`document_revisions`、`private_settings` 与对应加密密钥，保留密码哈希和版本，不复制本机会话、限流桶或重置密码。迁移只能写入经过确认的目标库，禁止用空白导入覆盖已有业务数据。

## 3. 部署两个 Worker

为管理 Worker 配置 Node URL 与内部密钥、`SETTINGS_ENCRYPTION_KEY`、`GITHUB_TOKEN`、`PUBLISH_TOKEN`、`MUSIC_DELIVERY_KEY` 与 `MUSIC_STREAM_ORIGIN`。加密密钥及 HMAC 密钥各自为随机 32 字节十六进制，不能相互复用；GitHub 凭据仅授权目标博客仓库内容写入。

音频 Worker 仅绑定同一个 D1、HMAC 密钥、`SITE_URL` 与可选中转预算，不持有解密或发布权限。先构建并预览：

```powershell
# 管理 Worker；构建前提供运行配置与 production 模式
npm.cmd run build -- --mode production
npx cf deploy --prebuilt --mode production --provision=false --secrets-file <private-secrets.json> --dry-run
# 核对结果后移除 --dry-run 部署

# 独立音频 Worker
cd music-worker
npx cf build --mode production
npx cf deploy --prebuilt --mode production --provision=false --secrets-file <audio-secrets.json> --dry-run
```

具体 CLI 参数以安装版本帮助为准。必须保证构建模式与部署模式一致。部署过程不自动开通 R2；默认不绑定私有素材桶。需要私有素材时自行开通、创建桶并在构建时设置 `ENABLE_PRIVATE_MEDIA=1`，先核对存储和操作费用。公开图床是另一个集成，配置自己的接口与 Token。

## 4. 部署博客

Vercel 导入自己的公开博客仓库。配置 `MUSIC_DELIVERY_ORIGIN=https://<admin-domain>`、`MUSIC_STREAM_ORIGIN=https://<audio-domain>`、三端一致的 `MUSIC_DELIVERY_KEY`；Robin 的 `DEEPSEEK_API_KEY` 留在服务端，修改后需重新部署。检查自己的 Bangumi 用户名、图片及字体，保留必要的公开素材与版权声明。

确认 GitHub 生产分支推送可以触发 Vercel 构建。控制台内容发布采用这个 Git 集成，不依赖自建 CI 回调。不要在管理端创建与公开仓库冲突的另一套内容来源；外部 Git 修改后，先核对再继续发布。

## 5. 运行验收与日常发布

- 管理登录页、静态资源和 HTTPS 正常；未登录无法读取文稿和集成秘密，原账号改密状态保持。
- 在控制台检查文稿数量、图床和书架配置，导入自己的音源并测试、启用。五渠道目录与音乐取源分别验证。
- 公开站的首页、文章、生活、音乐、书架及页脚管理链接可访问，手机布局正常。
- 抽查真实音频的 Range、媒体类型与浏览器实际起播；HTTP 上游经音频域名，不能回落 Vercel 整曲中转。不要把 206 或 health 作为完整播放证明。
- 发布一次现有公开内容，等待目标 `release.json` 与页面核验成功。旧快照、失败页面、构建未完成均不能显示成功；超过 30 分钟未确认后查看 Vercel 记录。

控制台保存草稿立即完成，正式发布等待构建；前台访客读取静态页面。日发布限流和五分钟后台核验减少重复操作，不能替代平台用量监控。

## 费用、备份与恢复

Vercel、Cloudflare Workers、D1 与 AI 分别计量。原站直连或独立音频中转只减少 Vercel 音频流量，仍消耗访客网络与边缘请求 / CPU。无损体积更大；中转支持滚动 31 个 UTC 日桶预算，0 代表仅监测，正数启用硬上限。额度以当前套餐为准，不能把免费流量理解为无限制服务。

定期导出 D1，并将加密密钥、部署秘密和代码版本分开安全备份。回退公开站使用 Vercel 对应成功部署；回退 Worker 使用已审核版本。数据库迁移或业务内容恢复必须核对备份时间和关联数据，代码回滚不会恢复 D1 与密钥。停用音源会阻止新取源，已签发票据最长约 10 分钟自然失效。
